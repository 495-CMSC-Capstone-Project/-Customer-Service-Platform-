## Section 1: System Delivery and Integration

Our CMSC 495 team set out to address a practical computational problem that appears across modern support organizations: customers expect fast answers to routine questions, yet they also need a trustworthy path to human help when automation is incomplete or wrong. Over eight weeks of iterative coursework, the team delivered an integrated Customer Service Platform that connects a React and TypeScript customer interface to a FastAPI backend, persists conversations and related records in PostgreSQL, and calls an external AI provider through a provider-agnostic interface. The resulting system is not a slide-deck prototype alone; it is a working pipeline in which a signed-in demo customer can send a message, receive an AI response with confidence information, escalate when human review is warranted, and record resolution feedback for the live demonstration conversation.

The team’s problem-solving approach was modular and incremental. Rather than embedding AI calls and database access inside the browser, the architecture keeps the frontend focused on interaction while FastAPI validates requests, enforces conversation ownership for the demo customer identifier, coordinates AI orchestration, and manages persistence. Feature branches, pull requests, and GitHub Actions workflows supported that iteration by repeatedly checking backend tests, frontend quality gates, and build health. Those practices mattered because integration failures—duplicate message submissions, incomplete retries, or mismatched escalation state—are exactly the class of defects that appear late if teams only assemble components at the end. The final-release evidence package shows that the team treated integration as an ongoing engineering concern, not a last-week surprise.

Within that shared baseline, my individual contribution was deliberately additive. The organization repository remains the team artifact. On my GitHub fork, on branch `feature/sean-davis-agent-review-deploy`, I extended the final release with attributable enhancements. First, I implemented a prototype human-agent review queue: backend endpoints to list active escalations and claim an open ticket (`OPEN` to `IN_PROGRESS`), plus a frontend `/agent-review` page to refresh the queue, open the conversation, and claim work. Second, I added a confidence meter on AI chat bubbles so low demonstration scores are easier to notice, while still labeling the value as a demo score rather than calibrated accuracy. Third, I added Docker Compose packaging and deployment documentation so PostgreSQL, FastAPI, and the built frontend can run as containers for reproducible local continuous-delivery style evidence.

These changes strengthen the AI-integration story without overstating scope. The AI feature still provides first-line responses and escalation signals; my queue makes the human side of that handoff inspectable. There is still no live representative chat handoff, and authentication remains a prototype. The project therefore shows both successful team delivery of an integrated AI-supported system and the professional habit of extending a stable baseline with clearly owned, testable improvements.

## Section 2: Methodology and Performance Evaluation

Critically evaluating our methodology means asking whether our process resembles professional software engineering or only classroom convenience. On balance, the team’s approach aligns with iterative delivery, separation of concerns, and automated verification more closely than with ad hoc coding. The repository organization—frontend, backend, docs, scripts, and CI workflows—reflects maintainability goals consistent with long-standing software engineering guidance on modular design and configuration control. Pull-request review and CI checks echo the verification culture emphasized across IEEE software engineering practice: changes should be reviewable, testable, and repeatable. From a Software Engineering Institute perspective on risk and process discipline, the team also did something often skipped in academic projects: we documented residual risks, security limitations, and a roadmap instead of implying that green tests equal production readiness.

Quantitative evidence from the team’s final-release documentation supports a favorable—but bounded—quality claim. Backend evidence reports approximately sixty-six passing tests with about 90.93 percent overall coverage and an eighty percent minimum coverage gate in CI, plus PostgreSQL integration testing. Frontend evidence reports sixty-one passing tests across multiple files, with statement coverage near 90.28 percent and enforced thresholds for statements, lines, functions, and branches. A controlled local API benchmark—using an in-process client, isolated database, and mocked AI provider—recorded fifty of fifty successful measured requests with a median response time near 5.97 milliseconds and a ninety-fifth percentile near 6.71 milliseconds. Those numbers are meaningful as reliability and handler-baseline signals. They are not evidence of multi-region scalability, live-provider latency, or production concurrency, and the project documentation correctly warns against that overclaim.

Where the methodology is weaker is equally instructive. Authentication stores a customer identifier in browser `localStorage`, which is unacceptable as enterprise identity. The team documented the absence of a hosted production deployment pipeline even while CI was strong—an imbalance between continuous integration and continuous delivery. AI confidence is a demonstration score, and large-scale load testing was not demonstrated. My fork-level work responds to two documented gaps at course scale: a prototype agent review queue and Docker Compose deployment evidence with a verification guide, plus tests for list/claim behavior. Claiming those additions as production CD or live agent operations would be inaccurate. Professional evaluation requires naming strengths and gaps: our metrics show solid course-scale engineering; our limitations show where industry hardening would begin.

## Section 3: Professional Development Roadmap

Completing this capstone clarified that my next professional growth should be guided by the gaps we could measure, not only by technologies that sound impressive. Industry reports such as the Stack Overflow Developer Survey and GitHub’s State of the Octoverse continue to show strong demand for cloud deployment skills, DevOps automation, and AI-related development practices, while IEEE Computer Society discussions of trustworthy systems reinforce that reliability, security, and lifecycle discipline remain core professional competencies. Against that backdrop, I plan a twelve-to-eighteen-month roadmap with three concrete tracks.

First, I will deepen production identity and access management. Our prototype sign-in was sufficient for demonstration, but real customer-service platforms require authenticated users, role separation between customers and agents, and protected APIs. I intend to build small proof-of-concept services using modern OAuth 2.0 / OpenID Connect patterns and server-side session or token validation, then map those lessons back to systems like ours where agent queues must not remain anonymously callable.

Second, I will strengthen cloud continuous delivery and observability. Local Docker Compose is a useful step beyond “runs on my laptop,” yet employers expect hosted environments, secret management, rollback discipline, and visible health signals. My plan is to deploy a compact full-stack sample to a managed cloud target, wire a basic pipeline from pull request to deploy, and add structured logging plus health/uptime checks. That path directly extends the CI strengths already present in our capstone while closing the delivery gap we documented.

Third, I will study AI evaluation and safety practices for support assistants. Integrating an external model is only the first milestone; professional systems need clearer handling of low-confidence answers, prompt abuse, and escalation quality. I will practice offline evaluation sets for support-style questions, experiment with guardrail patterns, and learn enough observability around model failures to make escalation decisions more evidence-based than keyword heuristics alone.

To keep this roadmap executable, I will use quarterly checkpoints: one identity POC, one cloud deploy-with-pipeline POC, and one AI-evaluation notebook or service spike, each with tests and a short written retrospective. I will also continue reading primary sources—annual developer surveys, Octoverse summaries, and IEEE/SEI materials—so technology choices stay evidence-based rather than trend-chasing. The lasting lesson from CMSC 495 is not that our platform is finished, but that professional software engineering is the discipline of delivering an integrated system, measuring it honestly, and then improving the next weakest link with clear ownership. That is the adaptability I intend to carry into practice.
